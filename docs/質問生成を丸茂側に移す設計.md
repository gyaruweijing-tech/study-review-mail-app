# 質問生成を MulmoClaude（丸茂）側に移す — 設計書

**日付**: 2026-08-07
**宛先**: MulmoClaude（`（手元のフォルダ）`）で作業する担当
**依頼元**: 復習メール（`（手元のフォルダ）`）

---

## 1. なぜ丸茂側なのか

復習メールは、ノートから作った質問を「後輩キャラからの質問メール」として週1で本人に送る。
その質問の質が低いと、メールが「何の話だっけ」で終わって復習にならない。

質問を**復習メール側で Anthropic API を叩いて作る案は破棄した**。理由はコスト構造ひとつ:

- ノートは、ユーザーが本文を**丸茂のチャットに貼り付けて**作られる。その瞬間、丸茂はすでに
  本文を全部読んでいる。HTML記事もそこで生成している。
- つまり**質問を作るのに必要な読解は、取り込み時にすでに済んでいる**。
  後から API で同じ本文を読み直させるのは、同じ仕事への二度払い。
- 丸茂側なら現行プランのまま追加コストゼロ。API キーも増えない。

**結論: 質問は、ノートを取り込む瞬間に丸茂が作る。**

## 2. 調査でわかったこと（3点、うち2点は既存のバグ）

### 2-1. 丸茂はすでに「質問」を作っている

`.claude/skills/study-review/SKILL.md` の「contentのリッチHTML化ルール」に、
**アクティブリコール(暗記カード)** が定義済み:

```html
<details class="recall"><summary>なぜ○○なのか?</summary><div class="answer">...</div></details>
```

1ノートに3〜6個が目安、とまで書いてある。**この仕組みは新規開発ではなく、既存機能の兄弟**。

ただし `recall` と、メールで使う `questions` は**声が違う**。ここを混ぜてはいけない:

| | recall（既存） | questions（新規） |
|---|---|---|
| 誰が問うか | 自分で自分に（自問） | 後輩が先輩に（他問） |
| 答えの置き場 | 同じHTML内に模範解答あり | **答えは無い**。本人が説明する |
| 目的 | 読み返しながら思い出す | 説明させて定着を測る |

同じ理解から派生させてよいが、`questions` に模範解答を含めてはいけない（答えが同梱されたら
想起練習にならない）。

### 2-2. `mailHook` が同期のたびに消える（既存バグ）

`scripts/sync.mjs` の `REPO_OWNED` は:

```js
const REPO_OWNED = ["reviewStage", "nextReviewDate", "status", "lastSentDate", "questions"];
```

`mailHook`（メール件名のフック）が入っていない。丸茂側スキーマにも `mailHook` は無い。
よって `merged = {...incoming}` の時点で消え、復元もされない。
**手で書いた件名フックは、次の sync で無言で消滅する。**

→ 丸茂側が `mailHook` を持つようになれば、この穴は自然に塞がる。

### 2-3. 復習ステージの語彙が2系統ある（潜在バグ）

| | 値 |
|---|---|
| 丸茂 `reviewStage` | 新規 / 1回目 / 2回目 / 3回目 / 4回目 / マスター |
| 復習メール `STAGES` | 新規 / 1周目 / 2周目 / 3周目 / 定着 |

**この2つは別物の進行状態**（丸茂は画面で読み返す復習、メールは説明できるかの復習）。
既存ノートは `REPO_OWNED` で守られているので無事。しかし**新規ノートは守るべき既存値が無い**ため、
丸茂の値（例 `"3回目"`）がそのまま入る。すると `answer.mjs` の

```js
const index = Math.max(0, STAGES.indexOf(current));  // "3回目" → -1 → 0
```

で無言で「新規」に落ちる。**丸茂側は何も直さなくてよい。復習メール側で受け取り時に正規化する**（§4）。

## 3. 丸茂側にお願いしたいこと

### 3-1. スキーマに2フィールド追加

`.claude/skills/study-review/schema.json` の `fields` に追加:

| フィールド | 型 | 内容 |
|---|---|---|
| `questions` | 配列（下記） | 後輩が聞いてくる質問。**ちょうど3つ** |
| `mailHook` | string | メール件名用のフック。20字前後 |

`questions` の各要素:

```json
{
  "q":    "後輩が実際に口に出す質問。1〜3文",
  "hint": "後輩が勝手に立てた、微妙にズレた仮説。1文"
}
```

**コレクションのスキーマが入れ子配列を持てるか分からない。** 持てないなら:

- **代案B**: `questions` を `text` 型にして、中身を JSON 文字列として入れる。
  復習メール側で `JSON.parse` する（パース失敗時はフォールバックに落ちるだけなので安全）。
- **代案C**: スキーマを一切変えず、`content` の `<details class="recall">` から復習メール側が
  抽出する。ただし §2-1 のとおり声が違い、答えが同梱されているので**推奨しない**。

判断は丸茂側に任せる。**A（配列）→ B（JSON文字列）の順で検討してほしい。**

### 3-2. SKILL.md に生成ルールを追加

「**新しいノートを取り込む**」の節に、`questions` と `mailHook` も作る旨を追記してほしい。
ルール本体は以下をそのまま使ってよい:

> **questions（復習メール用の質問を3つ）**
>
> このノートは後日、「後輩エンジニアからの質問メール」として本人に届く。本人がノートを見ずに
> 自分の言葉で説明できるかを試す道具なので、以下を守る。
>
> - **ノートを読み返さずには答えられない**質問にする。見出しをなぞっただけの
>   「『対応策』のところ、これって結局どういうことですか？」は最悪。**具体的な語を本文から引用する。**
> - **一番説明しにくい所**を狙う。直感に反する主張・対比・因果関係・「なぜそうなるのか」。
> - 3つはバラけさせる。同じ論点を3回聞かない。
> - **答えを書かない。** `recall` と違い、questions に模範解答は含めない。
> - `hint` には後輩が勝手に立てた微妙にズレた仮説を1文で。これが「違う違う」と説明したくなる燃料になる。
> - 後輩は採点しない。「不正解です」ではなく「そこがまだピンと来なくて」の側の人格。
>   専門用語を使いこなさない。急に賢くならない。
>
> お手本:
>
> ```
> q:    レストランが本当に売ってるのは料理じゃなくて「席×時間」だ、って書いてあったんですけど…
>       お客さんって料理にお金払ってますよね？ 何がどう違うんですか？
> hint: 「回転率が大事」ってことですか？ でもそれ、普通に当たり前な気もして…。
>
> q:    学習用のデータセンターは集中させて、推論用は分散させる、って真逆なのが謎です。
>       どっちも同じGPUを置いてるのに、なんで置き方が逆になるんですか？
> hint: たくさん集めたほうが速いんじゃないんですか…？
> ```
>
> **mailHook** — メール件名に使う20字前後のフック。答えを言わずに引っかかりだけ作る。
> 例: 「レストランが売ってるのは、料理じゃない？」

### 3-3. スキルの実体は2箇所にある（編集前に必ず確認）

`SKILL.md` と `schema.json` は**同じものが2箇所に存在する**。2026-08-07 時点で両者はバイト単位で同一、
更新時刻も同じ（08-06 21:29）なので、どこかに同期・インストールの経路がある:

| パス | 位置づけ |
|---|---|
| `.claude/skills/study-review/` | Claude Code がスキルとして読む側 |
| `data/skills/study-review/` | `server/workspace/paths.ts` の `skillsStaging`。コメントに「writes `data/skills/<slug>/{SKILL.md,schema.json,templates/*}` here」 |

**片方だけ編集すると無言で食い違う。** どちらを正として、どの経路で反映するのかは丸茂側の作法に従ってほしい
（`skillsStaging` という名前からすると `data/skills` に書いて `.claude/skills` へ入れる流れに見えるが、
外から断定はしない）。**編集後に両方が更新されていることだけは確認してほしい。**

### 3-4. 既存7本のバックフィル

`data/study-review/items/` に7本ある。復習メール側にはまだ4本しか入っていない。
新ルール導入後、**既存7本にも `questions` / `mailHook` を追加してほしい**（本文はすでに手元にある）。

ただし復習メール側の2本には**手書きの良い質問がすでに入っている**（`ai-infra-restaurant-harness`、
`ai-native-organization`）。これはお手本そのものなので、丸茂側で作り直す場合も
**上書きせず、まず現物を見てから**にしてほしい。取り込み時の衝突回避は §4 で復習メール側が担保する。

## 4. 復習メール側でやること（このリポジトリの作業）

丸茂側が入ったら、`scripts/sync.mjs` を次のように変える。**丸茂側の変更が入るまで着手しない**
（先に境界を反転すると、まだ `questions` を持たない丸茂のデータで既存の質問が消える）。

1. **`questions` / `mailHook` を `REPO_OWNED` から外す** → 丸茂側が正になる
2. ただし**「空で上書きしない」ガード**を必ず入れる:
   ```js
   // 丸茂側にまだ質問が無いノートは、リポジトリ側の既存を残す
   if (!Array.isArray(incoming.questions) || incoming.questions.length === 0) {
     merged.questions = existing?.questions;
   }
   ```
   これが無いと、丸茂が未対応のノート1本で既存の良問が消える。
3. **`reviewStage` を受け取り時に正規化する**（§2-3）。丸茂の語彙は復習メールの語彙と別物なので、
   **新規取り込み時は常に `"新規"` から始める**のが正しい。丸茂側の進行度は持ち込まない。
4. `REPO_OWNED` に残るのは `reviewStage` / `nextReviewDate` / `status` / `lastSentDate` /
   `answers`（回答履歴）。**これらは GitHub Actions が書き換えるので絶対に上書きしない。**

変更後の同期の境界:

| 持ち主 | フィールド |
|---|---|
| **丸茂が正** | title / date / source / tags / summary / content / **questions** / **mailHook** |
| **リポジトリが正** | reviewStage / nextReviewDate / status / lastSentDate / answers |

覚え方: **「教材と、教材から作れるもの」は丸茂。「誰がいつ何と答えたか」はリポジトリ。**

## 5. 手順

1. 丸茂: schema.json に2フィールド追加（案A→B）
2. 丸茂: SKILL.md に §3-2 のルールを追記
3. 丸茂: 既存7本をバックフィル（§3-4）（手書き2本は現物確認のうえ）
4. 復習メール: `sync.mjs` を §4 のとおり変更（**1〜3が終わってから**）
5. 復習メール: `node scripts/sync.mjs` → `git diff` で**質問が消えていないこと**を目視確認
6. 復習メール: `DRY_RUN=1 node send.mjs` でメール本文を確認 → commit & push

**5 の目視確認は飛ばさないこと。** 境界を反転する変更なので、事故の出方が「無言でデータが消える」型になる。
